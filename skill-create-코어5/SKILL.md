# /skill-create — 스킬 제조 공장

> **PO의 철학:**
> "가져다 쓰지 마라. 분해하고, 결함 부분은 걸러내고, 검증된 부품만 가려내 조립하라.
>  발굴 자체가 실력이 아니라 — 발굴 + 검증 + 자기 자산화까지 가는 흐름이 실력이다."

**필요한 Claude Code 스킬을 막연한 요청 한 줄에서 받아, 완성·검증된 `SKILL.md`로 출하하는 메타 스킬 — 스킬을 만드는 스킬.**

> **⚠️ 제조 대상 한정 (V3.2):** 이 스킬은 **Claude Code 스킬** — `~/.claude/skills/{name}/SKILL.md` 형태로 등재되어 슬래시 명령(`/{name}`)으로 호출되는 절차·방법론 단위 — 만 제조한다. LLM 의존형 독립 에이전트(웹사이트·데몬·API 등 자체 실행체) 제조는 형제 공장 `/에신-llm-dependent-agent-create`가 담당한다 (둘은 같은 9-Phase 방식·같은 "분해·검증 후 조립" 철학을 공유하며, 같은 자산이 스킬로 출하될 수도 에이전트로 재포장될 수도 있는 양방향 관계다).

이 스킬은 공개 저장소의 기존 스킬을 **통째로 신뢰하지 않는다.** 발굴물을 작업대에 올려 부품(Phase 블록·프롬프트·체크리스트) 단위로 검증하고, 안전하지 않은 부분을 걸러낸 뒤 검증된 부품만 적용한다. 그 위에 자체 작성을 얹어 조립하고, QC 출하검사를 통과한 것만 자산으로 등재한다. **출하 후에는 운영 루프**가 돌면서 사용 통계·피드백을 Phase 1로 회귀시켜 다음 사이클을 시작한다.

---

## 공장 비유 (Manufacturing Metaphor)

```
원자재 입고   →  공개 저장소·OSS·사내 자산에서 부품 발굴
입고 검사     →  발굴물 5대 KPI 검증
안전성 진단   →  주작-sal-da 방식 위험도 감사 — 결함 부분 식별
해체·선별     →  부품 단위 분해 / 결함 부분 걸러내기 / 검증된 부품만 선별
부품 창고(BOM)→  검증 통과 부품 목록 (5분류: 🟢🟡🔴🏭🔵)
조립          →  검증 부품 + 자체 작성 결합 → SKILL.md
출하 검사     →  4단 QC (정적·동적·호출·가드) + V1(Sonnet 5) 1회 → V2(Codex, L 규모만) 1회 — 합격 ≥95
출하          →  ~/.claude/skills/ 등재 + CLAUDE.md 기록
운영·개선     →  사용 통계·피드백 → Phase 1 회귀
```

핵심은 **"부품 선별·조립·운영 루프"** — 공급원에서 부품을 받되 결함은 걸러내고 검증된 부품만 가져다 조립하며, 출하 후에도 피드백을 다음 사이클로 환류시킨다.

## 핵심 원칙 (8대 철칙)

1. **발굴물 무신뢰** — 공개 저장소·사내 자산도 통째로 가져다 쓰지 않는다. 반드시 분해·검증한다.
2. **부품 단위 선별** — 발굴물 전체가 아니라 검증된 부품(Phase 블록·프롬프트·체크리스트)만 추출한다.
3. **운용 충돌 0건 — 타협 불가** — PO 글로벌 헌법(한국어 출력·보안 가드·SAL/MBO 자동 감지)을 깨는 부품은 기능이 아무리 좋아도 적용 거부한다.
4. **10라운드 + α 문답 항상 강제** — 막연한 요청을 그대로 받지 않는다. 모드에 맞춰 묻고 답해 스펙을 외부로 끌어낸다.
5. **MBO 승인 게이트** — Phase 2 PO 승인 없이 제조(Phase 3 이후) 시작 금지.
6. **자기검증 금지** — 제조한 스킬을 제조자가 검증하지 않는다. 별도 V1(Sonnet 5 읽기전용)·V2(Codex GPT-5.6 Sol 외부검증, 폴백 Opus 5 Teammate)를 투입한다.
7. **"파일 생성 ≠ 동작함"** — `~/.claude/skills/`에 SKILL.md가 있는 것만으로 완료가 아니다. **실제 슬래시 호출로 의도대로 작동**해야 완료다.
8. **자산화·운영까지가 완료** — 만들고 끝이 아니다. 등재 + CLAUDE.md 기록 + 운영 루프 가동까지 해야 출하 완료다.

### 스킬 특화 4대 원칙 (V3.2 유지)

- **단일 책임** — 하나의 명확한 목적만. 여러 목적을 한 스킬에 욱여넣지 않는다.
- **자기완결** — 만든 스킬은 다른 스킬 참조 링크에 의존하지 않는다. 필요한 내용은 추려서 자기 폴더 안에 참조 자료로 둔다.
- **간결** — 500줄 이내 권장. 거대 스킬 금지.
- **구조 완비** — YAML frontmatter(`description`·`user-invocable`) + Phase 구조 + 사용 예시 + 금지사항 — 4요소.

## Phase 0. 시동 (Intake)

### Phase 0-0. 의존 스킬 확인 — mbo-천상 자동 설치·연결 (★V3.11 신설, 매 실행 자동)

이 스킬은 **`mbo-천상`(공개명 `mbo-skill`, 호출 `/mbo`)에 필수 의존**한다 — Phase 2 목표서·승인·MBO 파일 저장·Phase 8 결과 보고가 전부 거기서 온다. 착수 전 반드시 확인한다.

```
1. 탐지: ~/.claude/skills/mbo-천상/SKILL.md 또는 ~/.claude/skills/mbo/SKILL.md 존재?
   → 있으면 3(검증)으로 — 있다고 건너뛰지 않는다(이전 실행이 404 HTML·절단 파일을 남겼을 수 있음)
2. 없으면 자동 설치 (PO에게 1줄 고지 후 실행):
   Git Bash / macOS / Linux:
     mkdir -p ~/.claude/skills/mbo
     curl -fsSL -o ~/.claude/skills/mbo/SKILL.md https://raw.githubusercontent.com/SUNWOONGKYU/mbo-skill/main/SKILL.md
   Windows PowerShell 5.1 (curl은 Invoke-WebRequest 별칭이므로 curl.exe 또는 아래 명령):
     New-Item -ItemType Directory -Force "$HOME\.claude\skills\mbo" | Out-Null
     Invoke-WebRequest -Uri https://raw.githubusercontent.com/SUNWOONGKYU/mbo-skill/main/SKILL.md -OutFile "$HOME\.claude\skills\mbo\SKILL.md"
3. 검증: 파일 존재 + 첫 줄 '---' + 본문에 'MBO_SPEC_VERSION' 마커 있음. 하나라도 아니면 — `mbo/`(자동 설치본)이면 그 파일을 삭제하고 2로 회귀(1회만), 두 번째도 실패면 5; `mbo-천상/`(운영자 원본)이면 삭제하지 않고 바로 5(수동 확인 안내)
4. 연결: Skill 도구 목록에 /mbo-천상 또는 /mbo 가 보이면 그걸로 호출.
   안 보이면(세션 시작 후 설치라 미등록) → 그 SKILL.md 를 Read 로 읽어 절차를 그대로 수행. 재시작 요구하지 않는다.
5. 실패(네트워크 차단 등) → Phase 2 진입 금지. PO에게 수동 설치 안내:
   https://github.com/SUNWOONGKYU/mbo-skill
```

운영 환경(`mbo-천상` 설치됨)에서는 1에서 발견 → 2 건너뛰고 3(검증)만 수행. 공개본·운영본이 같은 절차 하나로 동작한다.

- 인자가 있으면 그것을 제조 대상으로 한다.
- 인자가 없으면 대화 맥락에서 "무슨 스킬을 원하는지 + 단일/배치 중 어느 모드인지" 도출한다.
- 도출 불가 시 PO에게 한 줄 질문으로 확인한다.
- ★V3.12 **원자재 질문(필수)**: "이 스킬을 만들 때 쓸 원자재(선행 스킬·SKILL.md·문서·체크리스트)를 직접 가져오셨습니까? 있으면 경로를 알려주세요." — 있으면 **발굴 경로 A**(그것만), 없으면 **경로 B**(공개 발굴). 답을 MBO 「제조 대상」 메타에 `발굴 경로` 행으로 적는다.

## Phase 1. 요구 발굴 — 모드별 10라운드 + α 문답 (V3.5 — 10라운드 기본)

**막연한 요청을 그대로 제조에 넣지 않는다.** 모드에 맞춰 한 번에 한 질문씩 진행한다.

### ★ V3.5 핵심 원칙 — 질문은 AI가 한다 + 초보자 친화

1. **묻는 주체는 AI(스킬)이다.** PO에게 항목 나열을 던져 일방적으로 답하라고 시키지 않는다. AI가 한 질문씩 던지고 → PO가 답하고 → 다음 질문.
2. **초보자도 답할 수 있는 질문이어야 한다.** 기술 용어를 그대로 쓰지 말고 **풀어쓴 뒤 예시 1~2개**를 동반한다.
3. **객관식·예시형 우선.** 가능하면 `AskUserQuestion` 도구로 2~4개 선택지 + "Other" 직접 입력 형태. 자유 서술은 정말 자유 답이 필요할 때만.
4. **10라운드 기본, 부족 시 추가.** 종료 신호가 안 나오면 라운드를 늘려 보강한다.

## Phase 2. 목표 정의 — mbo-천상 호출 + 승인 게이트 (★V3.11 — 양식 복제 폐지, 스킬 호출로 전환)

**목표서 양식·승인·MBO 파일 저장·결과 보고는 `mbo-천상` 스킬이 단일 출처다.** skill-create는 양식을 베끼지 않고 `mbo-천상`을 호출해 그 절차를 그대로 탄다. skill-create가 보태는 것은 딱 하나 — 스킬 고유 「제조 대상 — 스킬 요소 + 메타」 절을 목표서에 **삽입**하는 것뿐이다.

이 단계에서 스킬 **규모(S/M/L)를 확정**한다. 배치 모드는 자동으로 L 판정.

### 호출 규격 (skill-create → mbo-천상)

| mbo-천상 단계 | skill-create에서의 처리 |
|---|---|
| PHASE 1 Step 1 맥락 분석 · Step 2 스무고개 | **건너뜀** — skill-create Phase 1(10라운드 + α 문답)이 이미 수행. Phase 1 산출물(기획안·출력 대상 명세)을 mbo-천상 입력으로 넘긴다 |
| Step 3 AS-IS 조사 | 수행 — 현재 사람이 하는 방식(수작업)을 조사해 「현재 vs 목표」의 AS-IS 칸을 채운다 |
| Step 4 MBO 목표서 작성 | mbo-천상 양식(최상위 목표·현재 vs 목표·KPI·산출물·완료·검증 기준[공개본 명칭 「목표 달성 평가·검증 기준」+「자가수정 한도」]·실행 계획·리스크) **그대로** + 「최상위 목표」 바로 아래에 아래 **삽입 절**을 넣는다. 제목은 `MBO 목표서 — 스킬 제조: {스킬명/카탈로그명}` |
| Step 5 PO 승인 | mbo-천상 게이트 그대로. ⛔ 승인 없이 Phase 2.5 이후 진행 절대 금지. 수정 요청 시 재제시 |
| PHASE 2 MBO 파일 저장(공개본 명칭 「목표서 파일 저장」) | **skill-create 작업 폴더**(Phase 0에서 지정) 루트에 `YYYY_MM_DD__HH.MM_mbo-천상_{스킬명}.md` 저장 — 컴팩션·세션 교체 대비 |
| PHASE 2 자율 실행 | skill-create Phase 2.5 → 9 가 곧 실행 계획. 실행 계획 표의 Task = skill-create Phase 목록 |
| PHASE 3 결과 보고 | skill-create Phase 8 출하 보고서 직후 `/mbo-천상 report`(공개 설치본 `/mbo report`) 로 KPI 실측·산출물·검증 대조 → 저장한 MBO 파일 하단에 덧붙임. 자가수정 게이트(미달 시 Phase 7 QC 또는 Phase 2 재승인 회귀)도 mbo-천상 규정 따름 |

KPI 작성 시 skill-create 고유 제약(mbo-천상 양식 위에 얹음):
- 반드시 **사용자 여정 KPI 1개 이상** — "파일 생성"은 데이터 KPI일 뿐
- "실제 슬래시 호출 시 의도대로 작동" 같은 호출 KPI 필수
- 실행 계획 표에는 skill-create Phase 2.5·3·4·5·6·7·8·9 를 Task로 나열

- 경로 A에서 원자재가 요구를 못 채우는 부품이 나오면 **🏭 자체 작성**이 기본. 밖에서 가져오려면 PO에게 "경로 B로 부분 전환" 승인을 받고 그 부품 1건만 발굴한다 — 조용히 섞지 않는다.
- 경로 A 원자재의 라이선스 판정은 「부품을 실제로 가져올 때 통과할 게이트」 그대로(PO 소유 확인 / 공개 코드 LICENSE / 불명은 패턴만).
- 실습·교육에서는 경로 A가 기본이다(90분 내 완주 목적) — 리서치·발굴을 빼고 「분해 → 도메인 교체 → 조립 → 실행 확인」에 시간을 쓴다.

이미 잘 만들어진 것을 찾는다. 시간은 PO만이 만들 수 있는 부분에 쓴다. (아래 출처·게이트는 **경로 B**에 적용, 라이선스 게이트는 양쪽 공통)

### ★V3.10 신설 — 부품을 실제로 가져올 때 통과할 게이트

> 참고만 할 때는 해당 없다. **복사·재단해서 넣는 순간** 아래를 지킨다. (근거: 에신 V3.12 — 제작자 선행 프로젝트 제조 회귀)

**1) 라이선스는 두 경로로 가른다**

| 유래 | 판정 | 통과 시 |
|---|---|---|
| 공개 코드·스킬 | LICENSE·저장소 이력 확인. 불명이면 🔴 컷 | 복사·재단 가능(고지 이행) |
| **PO 소유 내부 자산** | 파일에 LICENSE가 없어도 **소유 확인으로 판정**. 자산명·확인자·확인일 기록 | 복사·재단 가능 |
| 유래 불명 | 어느 쪽도 확인 불가 | **패턴 참고만** — 복사 금지, 재구현 |

파일에 라이선스 문서가 없다는 이유만으로 내부 자산을 외부 불명 코드로 오판하지 마라. 반대로 한 번의 구두 확인을 다른 자산까지 확대하지 마라.

**2) 재사용 원장** — 실제 재사용·의존이 있을 때만: `SOURCE_REUSE_LOG.md`(무엇을 어디서 → 어디에, 버전·커밋·해시) + `THIRD_PARTY_NOTICES.md`(라이선스 고지). 없으면 취약 버전 교체·회귀 추적·저작권 감사가 불가능하다.

**3) 벤치마크 입고 카드** — PO가 지정한 선행 스킬을 "구조 참고"가 아니라 **공급원**으로 쓸 때: `원본 경로 · 소유권 · 라이선스 판정 · 파일과 심볼 · 원본 해시 · 적용 위치 · 수정 내역`.

**4) 정보구조 계층 보존** — 벤치마크의 구성을 가져올 때 **상위 분류를 빼고 하위 항목만 옮기지 마라.** `원본 영역 → 상위 분류 → 하위 항목 → 상태`를 표로 만들고 산출 스킬에 각 계층이 남았는지 확인한다. 의도적 생략은 사유와 PO 승인을 기록.

### 4-1. 입고 검사 — 후보별 5대 KPI 채점

[🏭 자체 작성 필요]

🔵 공통부 부품의 예 (배치 모드 시):
- 공통 입력 검증 프롬프트
- 표준 산출물 양식 (예: HTML 보고서 구조)
- 공통 검증 체크리스트
- 카테고리 공통 사용 예시

배치 모드는 🔵가 반드시 채워진다. 단일 모드에서는 🔵 불가.

### 4-5. 이중 분류 규칙 (V3.2 신설 — 🔵 ∩ 🏭 교집합 처리)

한 부품이 여러 분류에 동시 해당할 수 있다. 다음 우선순위 규칙으로 단일 레이블 부여:

```
🟢/🟡  >  🔵  >  🏭  >  🔴
```

**판정 절차**:
1. **출처 우선** — 발굴물에서 가져온 것이면 🟢/🟡
2. **범위 우선** — 자체 작성이지만 N 스킬이 공유한다면 🔵 (배치 모드만)
3. **신규 작성 단독 사용** — 🏭
4. **결함** — 🔴 (다른 분류와 동시 적용 불가)

BOM 작성자는 한 부품을 두 분류에 동시 기입하지 않는다 — 단일 레이블만.

### 5-2. V1 설계 검증 — 이진 체크리스트 12항목 (문서만, 코드 미실행)

12항목(각 O=소거됨/X=잔존, 배점 없음):

2. 관계도에 이 요소들이 전부 노드로 존재하는가
3. 흐름도가 시작→종료까지 끊긴 경로 없이 연결되는가
4. 관계도에 붕 뜬(어느 화살표에도 연결 안 된) 구성요소가 없는가
5. plan.md 각 항목이 목표서(mbo) 승인 내용과 일치하는가
6. BOM 에 🔴(걸러냄) 부품이 남아있지 않은가
7. BOM 부품에 라이선스 미상·금지 라이선스가 없는가
8. plan.md 에 실패 모드(에러·한계 상황) 정의가 있는가
9. BOM 각 부품이 스킬 요소 중 최소 하나에 매핑되는가
10. 제조 모드(단일/배치)·스킬 규모(S/M/L) 결정이 plan §1 좌표에 명시됐는가
11. 관계도·흐름도 SVG 가 plan.md 최신 버전과 절 번호 1:1 로 대응하는가
12. 📡 출력 대상 시스템 명세(외부 출력 있는 스킬만)·🤖 선정 알고리즘(큐레이션·필터링형만)이 plan.md 에 빠짐없이 채워졌는가

## Phase 7. 출하 검사 — QC 4단 (V3.2, ★V4.4 범위 축소)

**자기검증 금지. 출하 검증은 여기서 단 한 번**(설계 검증은 Phase 5 에서 이미 끝났다). 제조에 참여하지 않은 **V1(Claude Code Teammate·Sonnet 5, Phase 5 V1 과 다른 세션) 1회 → V2(Codex, 폴백 Opus 5 Teammate) 1회(L 규모만)** 순으로 투입한다 — 「검증 편제」 절. V1 입력 = SKILL.md + 검증 기준(7-5) + Phase 5 설계 검증 보고서(`_design/phase5_design_verify.md`). ★ 설계 적합성(스킬 요소 누락·흐름 끊김 등)은 Phase 5 에서 이미 검증됐으므로 다시 보지 않는다 — 「구현(SKILL.md 본문)이 설계대로인가 + 실제로 도는가」에 집중한다.
(출처: SUNNY AI MAGIC 50 #28 / review-evaluate-코어1)

### 7-0. V1·V2 소환 메커니즘 (V3.2 신설, ★V3.11 편제 반영)

"별도 V1을 투입한다"는 선언만으로는 V1.0처럼 자기검증으로 회귀할 수 있다. 다음 메커니즘을 강제한다:

**소환 절차 (4단계 — 모두 필수)**:

1. **별도 Agent 도구 호출** — V1은 `Agent(subagent_type="general-purpose", model="sonnet", mode="auto")`(Sonnet 5) Teammate로, V2는 Codex CLI(탐지 통과 시) 또는 `model="opus"` Teammate 폴백으로 띄운다. 제조 세션·제조 Subagent가 자기 자신을 검증하지 않는다.
2. **제조 컨텍스트 비전달** — V1 prompt에는 SKILL.md와 **검증 기준**만 전달. 제조 과정의 의도·근거·내부 결정 사항은 전달 금지 (편향 차단).
3. **외부 검증 도구 사용 의무** — YAML frontmatter 검증·markdown lint·slash 호출 시뮬 등 **외부 도구 결과**를 함께 보고.
4. **호출 증거 기록** — Phase 8 출하 보고서의 "QC 결과" 항목에 `verification_agent_invocations: N` 카운트 + 호출 시각·duration 명시.

**금지**:
- ❌ 제조 Subagent에게 "이제 검증해라"라고 추가 지시
- ❌ 메인 Claude Code(SA)가 직접 검증 의견 작성
- ❌ Subagent 호출은 하지만 prompt에 제조 과정을 다 보여줘서 편향 유도

**위반 시 효과**: QC 결과 무효 처리, Phase 7 처음부터 재실행.

> **★V3.11/V3.12**: 검증 루브릭·절차는 본문 내장 그대로(외부 스킬 위임 아님). 검증 주체는 「검증 편제 — 작성자 · V1 · V2」 절, 판정 기준은 7-5 참조.

### 4단 QC

모든 규모에 공통 — 강도는 규모별 차등.

#### 7-1. 정적 분석
- YAML frontmatter 유효성 (필수 필드 존재·문법 OK)
- Markdown 구조 (헤더 계층·표·코드 블록)
- Dead 링크 검사 (외부 URL·참조 파일 경로)
- 시크릿 누출 검사 (정규식 패턴)
- 500줄 초과 여부

#### 7-2. 동적 검증
- 슬래시 호출 시뮬 — `/{스킬명}` 인식 여부
- 인자 처리 — Phase 0 인자 처리 로직 검증
- 외부 도구 의존 확인 — `Skill`/`Agent`/`Bash` 등 권한 매핑

#### 7-3. 실제 호출 검증 ★"파일 생성 ≠ 동작함" 7번 철칙 실행
- **실제 슬래시 호출 1회** — 가벼운 시나리오로 의도대로 작동하는지
- 산출물 검증 — 기대한 형식·내용으로 출력되는지
- **금지**: "파일이 ~/.claude/skills/에 있다"만으로 OK 처리

#### 7-3+. ★ 출력 대상 시스템 실제 화면 확인 (V3.5 신설 — 형제 공장 회고 흡수)

**"외부 시스템 출력" 정의 (V3.5 명확화)** — 다음 중 하나라도 해당하면 외부 출력:
- 웹사이트·블로그·커뮤니티에 글/이미지/댓글 게시 (예: WAAT 사이트, 노션 페이지)
- 파일 시스템에 사용자가 직접 열어볼 결과 파일 생성 (예: SVG·PDF·PPTX·이미지·HTML 산출물)
- DB·시트에 사용자가 다시 읽을 행 INSERT (예: Supabase, Google Sheets)
- 메신저·이메일·SMS 전송 (예: Slack, 카톡봇, Gmail SMTP)
- CLI 콘솔에 사용자에게 보일 텍스트 출력 (단, 디버그 로그·진행 안내는 제외)

**면제 — 다음만 하는 순수 스킬은 해당 없음**:
- INSTRUCTION 텍스트를 컨텍스트에 주입만 하고 별도 파일·외부 호출 없는 스킬
- Claude Code 내부 상태(메모리·tasks·plan)만 조작하는 스킬

**외부 출력에 해당하는 스킬은 그 시스템의 실제 사용자 화면을 사람 눈으로 확인하기 전까지 Verified 처리 금지.**

- 자기 검증 금지의 구체 적용: 슬래시 호출 1회 통과 + 산출물 텍스트 확인만으로는 Verified 불가
- 검증 주체: 작성자 또는 제조 Subagent **금지** → PO 직접 또는 별도 V1(L 규모는 V2도)
- 검증 화면: 출력 대상 시스템에서 **일반 사용자가 보는 그대로의 화면**
- 검증 항목 (최소): 텍스트 렌더링(마크다운 raw 노출 없음), 라벨·배지 의미 일치, 클릭 가능 요소 동작, 모바일/데스크톱 양쪽
- **접근성(a11y) — 웹 UI/배포 산출물인 경우만 ★V3.7** — axe-core WCAG 2 A/AA **0 critical·0 serious**. 클릭·시각 검증은 색 대비·폼 라벨 누락·ARIA 결함을 못 잡는다(실서비스 2026-06-11 회고). (순수 SKILL.md·CLI 출력 스킬은 면제)
- **콘텐츠 교차오염 0 — 배치 모드(1b, N개 산출) ★V3.7** — 각 산출물의 설명·메타가 자기 기능과 일치, 타 산출물 문구 복붙·생성 템플릿 잔재 0 (배치 생성 버그로 무관 산출물에 설명이 복제된 실서비스 회고). 표본 정상이어도 전수/표본 확대 점검.
- 회고 사유: claude-news-agent (형제 공장 사례)에서 자기검증 모두 통과 후에도 PO 브라우저에서 마크다운 raw 노출 + 라벨 오용 결함 발견

#### 7-4. V1 → V2 순차 1회 (★V3.12 — 승격 조건 폐지)

V1(Claude)이 통과시킨 산출물을 **L 규모만** V2(Codex gpt-5.6-sol, 탐지 실패 시 gpt-5.6-terra 1회 → Opus 5 Teammate 폴백, 제조·V1 맥락 비전달)가 **1회** 교차 검증한다. V1(Claude)이 고점을 주면 같은 LLM 가족 편향을 의심한다.
- **|V1 − V2| > 3점**이면 V2가 찾은 결함을 수정하고 **그 항목만** V2에 재확인(전체 재라운드 없음).
- **V2가 채점 형식을 못 지켜 점수 측정 불가**면 `V2 미실시 (사유)` 표기 + V1 점수를 최종으로.
- 폴백을 썼으면 출하 보고서에 `V2: Claude 폴백 (사유)` 기록.
- S·M 규모는 V1 1회로 출하한다(V2 없음). 어느 경우든 **V1 없이 출하 금지**, L은 V2도 있어야 출하.
- 도메인 전문가 리뷰 (L 규모, 필요 시 PO에 의뢰)
- 공개 저장소 검증 — 발굴한 부품의 라이선스·최신성 재확인
- 외부 표준 적합성 — 한국어 출력·보안 가드 등 헌법 통과

| **사양 충족률** | 25 | MBO 최상위 목표·KPI·산출물 표 대비 실제 구현 비율. plan.md·BOM 대로 구현됐는지 포함 |

> **제거된 축 — 「구조 완성도」(구 15점, YAML frontmatter·핵심 원칙·Phase 구조·필요 도구 전부 있음·500줄 권장)**: 스킬 요소 누락은 Phase 5 설계 검증 이진 체크리스트 1·2·9번 항목으로 이관됐다. Phase 7 은 "SKILL.md 가 실제로 그 구조대로 존재하는가"만 7-1 정적 QC 에서 확인한다(점수 아님).

**합격선(하드 게이트)**: **총점 ≥ 95** AND **Critical·High 결함 0** AND **4단 QC(7-1 정적·7-2 동적·7-3 실호출·7-3+ 화면 확인[해당 시]) 전항 O** AND 사용자 여정 KPI 통과. 하나라도 아니면 불합격.

**불합격 처리(라운드 재발 방지)**: 작성자가 결함을 수정 → 검증자에게 **그 결함 항목만** 재확인 요청 → 검증자는 재채점하지 않고 "소거됨/잔존" 이진으로 답한다. 잔존이면 Phase 6 회귀(구조 문제). 전체 재라운드 없음.

**V1 → V2**: V2는 같은 양식으로 1회 채점(L만). `|V1 − V2| > 3점`이면 V2가 찾은 결함을 수정하고 그 항목만 V2에 재확인. Medium·Low는 출하 후 Phase 9 개선 백로그(출하 보고서에 기재).

**혼동 금지**: 이 채점은 *제조 출하 검증*이다. 만든 스킬 내부의 자가 채점 루프(예: 100점 수렴형 스킬)는 *제품 품질 루프*이며 출하 판정 권한이 없다.

### 결함 발견 시
- 결함 수리: 작성자가 수정 → V1(또는 V2)에 **그 항목만** 재확인 요청. 전체 QC를 다시 돌리지 않는다. (`/5times-debug-loop`은 있으면 쓰는 선택 보조)
- 같은 결함이 재확인에서도 잔존하면 Phase 6로 회귀(구조 문제)

### 출하 판정 (V3.2 — 회귀 깊이 결정 표)

```
✅ 합격 — 7-5 합격선(V1·V2 총점 ≥95 · Critical·High 0 · 4단 QC 전항 O · 사용자 여정 KPI) 충족 → Phase 8 출하
❌ 불합격 — 결함 잔존 → 회귀 깊이 결정 표 적용
```

| 결함 유형 | 회귀 위치 | 판정 기준 |
|--------|----------|----------|
| 단순 문구·구조 결함 | **Phase 6 재조립** | 부품 변경 없이 조립 수정으로 해결 가능 |
| 부품 결함·BOM 분류 오류 | **Phase 4 재분해** | BOM 재산출 필요 |
| 정책 위반·KPI 미달·자기완결 위반 | **Phase 2 MBO 재승인** | 목표 자체가 달성 불가능한 구조 |

   - 피드백 수집 경로 (이슈 트래커·README의 연락처 등)

   - `.bat` 한글 echo·주석 금지 (cmd cp949 디코딩 사고 회피)

   - **★V3.9 동기화 — 바탕화면 바로가기 자동 생성 금지** (에신 V3.9에서 R7 폐지 + skill-create 자체 verify_env.ps1도 같은 취지로 폐지, PO 판단 2026-08-01). `install_shortcut.ps1` 을 만들지 않는다. 진입점은 폴더 안 `.bat` 하나로 충분. (에신 쪽 새 R7은 "사람 개입형이면 로컬 웹 GUI" — 그건 에이전트 영역이므로 스킬 공장은 차용하지 않는다)

## Phase 9. 운영·개선 — 피드백 루프 (V3.2 신설) ★

**출하는 끝이 아니라 운영의 시작이다.** Phase 9는 자율 루프 — 일상 운영 중 수집된 데이터가 다음 사이클의 Phase 1로 회귀한다.

### 9-1. 운영 모니터링

- **사용 횟수** — 스킬이 실제로 호출되는 빈도 (수동 기록 또는 슬래시 호출 로그)
- **이상 신호** — 호출 0회 / 같은 오류 반복 / 응답 시간 급증
- **사용자 여정 KPI** — Phase 2에서 정의한 지표를 일상적으로 추적

### 9-2. 피드백 수집

- **이슈 트래커** — GitHub Issues 또는 README의 연락처
- **자동 수집** — 실패 패턴 로그
- **PO 인터뷰** — 분기·반기 단위 정성 피드백

### 9-3. 개선 사이클 → Phase 1 회귀

피드백이 일정 수준 누적되면 다음 사이클을 트리거. 다음 **정량 임계값** 중 하나라도 충족 시:

**자동 트리거 조건 (OR)**
- **사용률 0** — 출하 후 30일간 호출 0회 (폐기/통합 검토)
- **반복 실패** — 같은 오류 ≥ 3회 (직전 7일)
- **피드백 누적** — "버그·개선요청" ≥ 3건 (직전 14일)
- **PO 정기 점검** — 매월 1일 운영 KPI 리뷰 (강제)

**트리거 발동 후 회귀 깊이 매핑**:

| 트리거 신호 | 회귀 깊이 |
|--------|----------|
| 단순 문구·예시 수정 (피드백) | Phase 6 재조립만 |
| 부품 변경·새 절차 추가 (반복 실패) | Phase 4 재분해부터 |
| 정책·구조 변경 (정기 점검) | Phase 2 MBO 재승인부터 |
| 사용률 0 스킬 폐기 결정 | Phase 8 자산 갱신 + Phase 9 폐기 절차 |

### 9-4. 점진적 배포 (Canary)

L 규모 스킬은 다음 사이클 산출물을 한꺼번에 풀지 않는다:
- **Canary** — PO 본인이 1주 선행 사용 → 안정 확인
- **Rollout** — 팀 또는 공개 배포
- **Rollback** — 문제 발견 시 즉시 되돌릴 수 있는 경로 (이전 버전 폴더 백업)

### 운영 루프 종료 조건

스킬 폐기·교체·통합 시점까지 무한 루프. 폐기 시:
- CLAUDE.md 등재 갱신 ("폐기" 또는 "후속 스킬로 이관")
- 사용 로그 아카이브

## 금지 사항 (안티 패턴 V3.2 — 10개)

❌ **절대 하지 말 것**:

1. **통째 채택** — 발굴물을 분해 없이 그대로 가져다 쓰지 않는다 (Phase 4 필수).
2. **결함 적용** — 🔴 판정 부품을 "기능이 좋으니까"로 되살리지 않는다.
3. **운용 충돌 묵인** — 헌법 위반 부품을 글로벌에 들이지 않는다 (타협 불가).
4. **10라운드 + α 문답 생략** — "요청이 명확하다"는 자가 판단으로 Phase 1을 건너뛰지 않는다.
5. **MBO 게이트 무시** — PO 승인 없이 제조 시작 금지.
6. **자기검증** — 제조자가 자기 스킬을 QC하지 않는다.
7. **"파일 생성" 합격 처리** — ~/.claude/skills/에 파일이 있다는 것만으로 출하하지 않는다. 실제 호출로 검증.
8. **거대 스킬 + 외부 참조 의존** — 단일 책임 위반·자기완결 위반 금지. 500줄 권장 초과 시 분할 검토.
9. **모드 무선언** (V3.2) — 단일/배치 모드를 명시하지 않고 진행하지 않는다.
10. **운영 루프 단절** (V3.2) — Phase 9 진입 없이 "출하 완료"로 종결하지 않는다.
